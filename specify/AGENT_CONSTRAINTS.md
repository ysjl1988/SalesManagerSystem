# 智能体开发约束规范

> **文档版本**: v1.1  
> **创建日期**: 2026-03-27  
> **适用范围**: 本智能体（Kimi Code CLI）在 SalesManagerSystem 项目中的所有开发活动

---

## 约束一：中文优先原则

### 说明
所有回复、文档、代码注释均使用中文。技术术语可保留英文（如 HTTP、API、CSS 等）。

### 执行要求
- [x] 回复用户使用中文
- [x] 编写文档使用中文
- [x] 代码注释使用中文
- [x] 变量命名遵循项目现有规范

---

## 约束二：文档先行原则

### 说明
任何需求开发都必须先进行文档编写，经用户确认后再进行编码。

### 文档要求
每个需求文档必须包含：
1. **需求描述** - 功能背景、要求、验收标准
2. **设计方案** - UI设计、技术选型、架构设计
3. **实现方法** - 具体的实现步骤、代码结构
4. **测试验收条件** - 功能验证的具体标准
5. **测试案例** - 单元测试、UI测试等测试代码

### 执行流程
```
用户提出需求
    ↓
创建需求文件夹（specify/active/XXX-需求名称/）
    ↓
编写需求文档（specify/active/XXX-需求名称/XX-需求名称-feature.md）
    ↓
与用户讨论确认
    ↓
文档定稿，开始编码
```

### 文档存放规范

#### 目录结构
```
specify/
├── README.md                      # 项目看板（状态追踪）
├── AGENT_CONSTRAINTS.md           # 本文档
├── active/                        # 进行中/已完成未满2个月的需求
│   ├── 001-password-toggle/       # 需求文件夹（序号-简短描述）
│   │   └── 01-password-toggle-feature.md
│   ├── 002-sales-module/
│   │   ├── 02-sales-module-requirement.md
│   │   ├── 02-sales-module-design.md
│   │   └── attachments/           # 附件（设计稿、截图等）
│   └── 003-data-export/
│       └── 03-data-export-feature.md
│
└── archive/                       # 归档区（按季度组织）
    ├── 2026-Q1/
    │   └── 001-password-toggle/
    └── 2026-Q2/
```

#### 文件夹命名规则
```
active/序号-简短描述/

要求：
- 序号：3位数字，从 001 开始连续编号
- 描述：小写英文，单词用短横线连接
- 不在名称中体现状态（状态由看板管理）

示例：
✅ 001-password-toggle
✅ 002-sales-data-module
✅ 003-batch-user-import
```

#### 文档命名规则
```
XX-需求名称-feature.md    # 合并文档（简单需求）
XX-需求名称-requirement.md # 需求文档（复杂需求拆分）
XX-需求名称-design.md      # 设计文档（复杂需求拆分）
XX-需求名称-impl.md        # 实现文档（复杂需求拆分）

要求：
- 前缀与文件夹序号保持一致
- 使用两位数字前缀（01, 02...）
```

#### 归档规则
- **归档条件**: 需求状态为"已完成"且超过2个月
- **归档路径**: `archive/年份-季度/`
- **归档示例**: `specify/archive/2026-Q2/001-password-toggle/`

## 约束三：文档驱动编码原则

### 说明
编码必须按照任务顺序逐一执行，任何修改都要先更新文档再编码。

### 执行要求
1. **按序执行** - 按照文档中规划的任务顺序逐一完成
2. **文档先行** - 如需修改设计，先更新文档，再修改代码
3. **实时同步** - 文档状态要与实际开发状态保持一致

### 文档状态流转
```
设计中（等待确认）
    ↓ 用户确认
编码中
    ↓ 编码完成
测试中
    ↓ 测试通过
已完成
    ↓ 超过2个月
已归档（移到 archive/季度/）
```

---

## 约束四：自动验收原则

### 说明
编码完成后自动生成测试案例，并根据验收条件自动验证，通过后再告知用户完成。

### 执行流程
```
编码完成
    ↓
自动生成/更新测试案例
    ↓
运行单元测试
    ↓
运行UI测试（如需要）
    ↓
验证验收条件
    ↓
全部通过 → 告知用户已完成
有失败项 → 修复后重新验收
```

### 验收检查项
- [ ] 单元测试全部通过
- [ ] UI测试全部通过（如涉及页面修改）
- [ ] 功能符合需求文档描述
- [ ] 代码风格符合项目规范

---

## 约束五：复杂任务分解原则

### 说明
对于复杂的任务，可以分解为不同的开发任务后台执行，定时向用户汇报状态。

### 执行要求
1. **任务分解** - 将复杂任务拆分为多个子任务
2. **后台执行** - 子任务可以在后台并行或串行执行
3. **状态汇报** - 定时（或按里程碑）向用户汇报执行状态
4. **异常处理** - 遇到阻塞问题及时汇报，等待用户决策

### 状态汇报格式
```
任务名称：XXX
整体进度：X/Y 完成
当前状态：执行中/已完成/遇到阻塞
详细信息：
- 子任务1：已完成 ✓
- 子任务2：执行中 ...
- 子任务3：待开始
```

## 规范执行检查清单

每次开发任务开始前，自我检查：
- [ ] 是否已创建需求文件夹？（specify/active/XXX-xxx/）
- [ ] 是否已编写/更新需求文档？
- [ ] 文档是否包含完整的设计方案？
- [ ] 文档是否包含测试验收条件？
- [ ] 是否已得到用户确认？
- [ ] 是否按文档顺序执行任务？

开发完成后，自我检查：
- [ ] 是否已更新文档状态？
- [ ] 是否已添加/更新测试案例？
- [ ] 是否已运行测试并全部通过？
- [ ] 是否已验证所有验收条件？
- [ ] 是否已超过2个月需要归档？
